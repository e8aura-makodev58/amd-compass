Reference for application defense

Compass in one sentence

Compass is a synthetic multi-room operational control room that uses deterministic application logic to manage simulated demand and uses a bounded recommendation agent to rank eligible responders for one selected issue.

What it is not: Compass is not an HR system, payroll system, real plant controller, predictive-maintenance product, real-world scheduler, or legal/labor advisory tool. All people, equipment, maps, histories, and outcomes are synthetic and domain-neutral.

Question 1: capacity

The application deterministically selects which actionable unresolved issue may receive available capacity next.

Question 2: responder fit

Compass ranks only the application-supplied eligible responders for that one issue.

Application authority

The application validates, offers, assigns, resolves, audits, and persists every canonical transition.

Trust boundary and hidden simulation truth

Every synthetic responder has hidden ResponderSkill values by issue class: a true median repair duration and true success probability. These values make outcomes realistic, but are never exposed to operators, normal APIs, analytics, the event planner, Compass, audit prose, queue priority, or staffing logic.

Visible evidence

Observed case count, weighted median duration, success rate, reopen rate, and evidence strength. Small samples can disagree with hidden truth by design.

Hidden internals

True skill, RNG draws, work factors, contribution weights, raw attempts, and credentials. Public projections use allowlists and redact them.

Why this matters

Compass must reason from public observed evidence and uncertainty, not privileged simulation knowledge or a synthetic employee score.

Architecture and control-room state

Control Rooms

Plant #1 and Plant #2 have independent Live/Offline state, clock, RNG streams, personnel, equipment, issues, assignments, analytics, workforce calendar, scenarios, and audit history. Provider settings and deployment-level logs are shared. Identical synthetic IDs in separate rooms are valid because room identity scopes them.

READY / FAILED = boot healthRUNNING / PAUSED = clock stateCanonical server state~1.5 second browser pollingRevision/conflict protection

Persistence

State is versioned JSON persisted through serialized clone → mutate → validate → atomic rename writes. Scheduler obligations carry durable tokens claimed before asynchronous work. Restart resumes from stored simulated time without wall-clock catch-up; unresolved corruption isolates only its room as FAILED.

End-to-end application flow

1. ClockAdvance simulated time only while running.
2. TriggerClaim a durable event, staffing, handover, offer, or resolution token.
3. DemandValidate event; create issue or deferred demand at the cap.
4. QueueDeterministically select the next pending issue when capacity exists.
5. PacketBuild public bounded candidates and deterministic baselines.
6. CompassOptional structured rank; otherwise deterministic fallback.
7. DispatchRevalidate, offer one at a time, accept/reject/override.
8. OutcomeAssign, move, resolve/reopen, audit, and refresh views.

Shift reviews, handovers, support, transfer, release, extension expiry, and temporary-repair obligations use the same durable trigger discipline.

Simulation, demand, and workforce

Clock and demand

Live Simulation supports 1×, 5×, 10×, and 60×. Normal issue opportunities occur at a persisted deterministic interval of 8–25 simulated minutes. Pausing advances neither simulation time nor due work. Trigger Next Event skips only waiting; it retains normal validation and demand limits.

At most 10 actionable unresolved issues may exist in PENDING, RECOMMENDATION_READY, OFFER_PENDING, or ASSIGNED. Excess demand becomes a Demo-only deferred demand record, not an issue eligible for dispatch.

Priority and queue

Critical: serious operational risk OR production impact ≥ 80 High: complex OR impact ≥ 45 OR age ≥ 8 hours (also age ≥ 20 hours) Standard: otherwise Queue order: Critical → High → Standard → oldest raised time → stable issue ID

Priority is deterministic and application-owned. Planning impact may inform synthetic impact but is not the only signal; models do not set priority.

Four-crew workforce

  • 24 synthetic responders: four crews × six people
  • Persisted 14-day 2-2-3 rotation
  • One normal crew at every 08:00/20:00 boundary
  • 12-hour normal duty; 12-hour minimum recall rest
  • 16-hour maximum continuous duty
  • Normal staffing 6; legal surge cap 8
  • Extension up to four hours; one lawful 12-hour call-in when needed
  • Public names use EngrNNN, TechNNN, or OptrNNN

Staffing reviews run at 06:00 and 18:00, plus rechecks after an issue raise, assignment release, escalation, or responder availability. Handover at 08:00/20:00 preserves lawful work or records an explicit replan; it never fabricates resolution or silently loses work.

Repair and temporary recurrence

An issue may resolve, fail and reopen, or resolve temporarily. A temporary repair has a deterministic 20% normal likelihood and 55% likelihood under Recurring temporary repairs; it creates exactly one linked recurrence 30–90 simulated minutes later. It does not create a permanent reduced-MTBF state.

Mathematics and algorithms

Simulation time

t_sim,new = t_sim,old + speedMultiplier × elapsedRealMilliseconds

Distance and travel time

d = √((x₁ − x₂)² + (y₁ − y₂)²) t_travel = d / (1.4 m/s × 60) + 1.5 × floorChanges [minutes]

Nearest Available uses minimum travel time, not merely planar distance, so a responder on another floor is not incorrectly treated as nearest.

Observed evidence

weighted success rate = Σ(contributionShare × successIndicator) / Σ(contributionShare) weighted reopen rate = Σ(contributionShare × reopenIndicator) / Σ(contributionShare)

Evidence labels: None = 0, Weak = 1–2, Moderate = 3–5, Strong = 6+ effective observations. Weighted median is the first sorted repair duration whose cumulative contribution reaches half of total contribution.

Visible naive comparator

naiveScore = 100 × successRate − 2 × medianResolutionMinutes − 3 × travelTimeMinutes

For no history, the naive comparator uses success rate 0 and median 60 minutes. It deliberately ignores evidence strength, creating a transparent contrast with Compass’s qualitative treatment of uncertainty.

Hidden outcome model

historyWeight = 0.30 × min(effectiveEvidence / 8, 1) median = (1 − historyWeight) × hiddenMedian + historyWeight × observedMedian successProbability = (1 − historyWeight) × hiddenProbability + historyWeight × observedSuccessRate

For two responders, with fastest/second work rates q₁/q₂ and synergy α = 0.60:

teamRate = q₁ + 0.60q₂ teamSuccess = min(0.98, highProbability + 0.60 × lowProbability × (1 − highProbability))

Work accumulates as min(remainingWork, elapsedMinutes × teamRate). Segment probabilities are combined by work completed. Force Resolve completes remaining work but uses the same stored success draw and probability; it cannot guarantee a successful result.

Settings and Demo

API configures the AMD Token Factory model and thinking level. Credentials remain server-side. Demo is room-scoped and contains Agent activity, Simulation overrides, Trigger Next Event, Force Resolve, scenario selection, workforce outlook, staffing/handover records, surge legality, and deferred-demand cap note.

Scenarios are Normal, Elevated demand, Personnel shortage, Recurring temporary repairs, and Auto. Analytics: hierarchy, meaning, and limits

Analytics reads one canonical room snapshot and one simulation timestamp. It is descriptive, not a priority engine or second database. Rates include denominators and are unavailable below three observations.

Shift first

Default operational view: latest 12 UTC day/night shift periods, aligned 08:00–20:00 and 20:00–08:00.

15-minute drill

Click a shift for its 15-minute lifecycle/downtime detail and linked issues/events, rather than showing dense detail by default.

Higher aggregation

Daily (08:00–08:00), weekly (Monday 08:00), and monthly (first day 08:00) summarize complete simulated history.

Period bars show issues raised/resolved, end backlog, station-minutes of downtime, deferred demand, staffing actions, and handovers. Current incomplete periods are labeled Partial; missing prehistory is labeled Insufficient history, never fabricated as zero. Backlog is replayed from lifecycle records at each boundary. Downtime unions intervals per station before summing so overlapping records cannot double-count a station.

Offline Demo

Offline Demo is a deterministic API-free fixture, not a broken Live mode. It contains a fixed issue, fixed candidates, stored Compass result, deterministic baselines, real offer/assignment/override actions, public audit, and reset. It needs no credentials, network, provider availability, or API spend.

Docker deployment and health

Compass runs in one hardened Node 22 Docker container on port 3000, using a named persistent volume for room state, metadata, provider settings, audit data, and application events. The image excludes secrets/local state, runs non-root with a read-only root filesystem, separate temporary storage, no added Linux capabilities, and no-new-privileges.

Health succeeds only when every configured room is READY. State migration is deliberate: back up state, validate an empty target volume, stop the previous writer, copy once, start the service, confirm health/revisions, and retain rollback material. A nonempty volume is never automatically merged or overwritten.

Defense questions and answers

Is Compass deterministic?
Application facts, eligibility, priority, staffing, simulation time, persisted RNG streams, outcomes, validation, persistence, and fallbacks are deterministic from stored state. Optional provider rankings/prose are not assumed deterministic and are revalidated.
Does Compass globally optimize the workforce?
No. The deterministic queue picks an issue eligible for capacity; Compass ranks responders for that one issue only. There is no unconstrained global workforce optimization.
Can a model send people, change shifts, or invent facts?
No. The model may only propose a bounded event or rank an application-supplied candidate set. The backend owns and validates all mutations.
Why keep hidden skill?
It supplies controlled synthetic ground truth for outcomes. It is deliberately unavailable to operators and Compass, preserving uncertainty and avoiding privileged synthetic performance scoring.
Does Force Resolve guarantee success?
No. It bypasses waiting, not outcome logic. The same attempt probability and stored random draw can reopen the issue.
Are the workforce rules real labor advice?
No. They are configured simulation constraints, not real employment, safety, payroll, or legal guidance.
What happens if two operators act at once?
They share canonical room state. Serialized mutation, revision checks, and eligibility revalidation reject stale/conflicting actions rather than silently making invalid assignments.

Verification posture and demonstration script

Compass uses hermetic backend tests (no provider/network calls and no production-data writes) and Chromium end-to-end tests with provider failures forced. Coverage includes room isolation, failure containment, clock speeds, durable triggers, queue caps, workforce legality, handovers, redaction, races, Live/Offline behavior, map interaction, accessible controls, analytics drill-down, and Docker build/health configuration.

Suggested defense walkthrough: open a paused room; select an active issue; show the deterministic nearest/naive comparators beside Compass’s bounded recommendation; explain that an operator can override; follow the event feed and Station Status; inspect the shift-first Analytics drill-down; then use Offline Demo to show the same workflow without a provider.
